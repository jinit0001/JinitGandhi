OpenTrace

A full-stack tool that scores your digital footprint risk, from the problem definition all the way to a working product.

Team projectRequirements · APIs · QAReact · Node · Express · MongoDB2026

The problem

Most people have no real idea what their public digital footprint says about them. A GitHub profile, a Reddit history, a few scattered posts: each is harmless alone, but together they can reveal patterns, habits and even security weak spots.

There was no simple way for an everyday person to see this the way an attacker, an employer or just a curious stranger might. So OpenTrace did not start as "let's build a cybersecurity tool." It started as: let's help someone see what is visible about them, and whether that is a risk.

Scoping it before building it

  • Who is it for? Everyday users who have never audited their own footprint, not security professionals.
  • What is the smallest useful version? Pull data from two high-signal sources (GitHub and Reddit), score the exposure, and explain why in plain language.
  • What does "done" look like? A person enters a profile and gets a risk score they can actually understand, not a wall of technical findings.

Narrowing to two sources let us ship something real and learn from it, instead of getting stuck on an endless version one.

What I owned

  • Requirements and workflow: input a profile, pull data through REST APIs, run AI-assisted risk scoring, and present results a non-technical user can act on.
  • API integration for GitHub and Reddit profile analysis, feeding the scoring logic.
  • Testing and QA, catching gaps before users would, and documenting the process for handover.
  • The translation layer. The hardest part wasn't the scoring. It was making the output make sense. A risk score with no explanation is useless.

Where it got hard

Partway through, it became clear that our original scope did not hold up. Some of the data we planned to score against was not as clean or as available as we had assumed. The tempting move was to patch around it and keep going.

Instead, I pushed to pause and rework the requirements properly: re-scope part of the workflow, get the team back on the same page about what we were building, and accept a short-term loss of speed. In return, we shipped something that held together.

What I'd do differently

I would write the acceptance criteria for each feature before building, so a mismatch like this shows up on paper instead of in code. The earlier a bad assumption is caught, the cheaper it is to fix.

Why this is the work I want to doOpenTrace was not a fixed-spec assignment. It began as an ambiguous problem, and every decision after that (what to build, what to cut, when to slow down) was ours to make and defend.
